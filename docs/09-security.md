# 09 · Security and privacy

## Tenancy
Every `app` table has RLS. Membership is derived from `auth.uid()` through `private` helpers; no policy trusts a
workspace id from the request. Scope narrows a membership to families and market nodes (a region id covers its
children). External members and `access_ends_at` are enforced in the same helpers. Staff access comes from
`app_metadata.nutrivo_staff`, which only the Supabase admin API can set. The web app uses the service role in one place: `/admin` reads
the staff tooling tables server-side after checking that flag on the person's own session (T-205); its writes are
the staff RPCs under that session, never the service role. The anon role reaches nothing in `app`
or `ref` and can execute only `verify_reference` and `coverage_snapshot`. On the hosted projects the grants are the
migrations' only: no table writes for anon or authenticated, no automatic exposure of new tables, and Queues never
exposed through PostgREST (D-26). New tables, views and sequences in `public` get no anon or authenticated grant by
default (#179 DB-9); a function there still revokes from public itself, because PUBLIC's EXECUTE is a global default.
`private.enqueue`, `private.write_audit` and `private.consume_allowance` are executable by the service role (and the
owner) only: clients reach them through the security definer RPCs (#179 X2). Every trigger function runs with
`search_path = ''` (#179 DB-17). The doctor's read-only `supabase-grants` check proves this on staging and production
(docs/16).

**Public verification (I04, T-406).** The `verify` Edge Function holds the anon key only, never the service role, so
it can execute `verify_reference` and nothing else. It answers status, issue date, ruleset version and whether Not
assessed items existed; a missing and a malformed reference get the identical `unknown` answer, so a caller learns
nothing about near misses. The page `/verify/[ref]` is `noindex` and `Referrer-Policy: no-referrer`, and no log line
carries a reference. Rate limits are best-effort and per instance: 30 a minute per visitor in the web app, 60 per client
and 1,200 per instance in the function. A shared limiter would need storage and is left to T-1103 (question on #48).

## The record
Insert-only tables (docs/03-data-model.md) have privileges revoked and a rejecting trigger, so even the service key
and the table owner cannot rewrite history. Certificates form a hash chain per workspace. Every event stamps the
actor's external flag and the ruleset version at write time.

## Tokens and files
Invitation, document-request and share tokens are 32 random bytes generated by the worker; only their SHA-256 is
stored; they expire and are single-use where it makes sense. Job payloads never contain tokens or secrets. An
invitation token is minted inside the `notify` job and exists only in that process and in the email; a retry mints
a new one, which replaces the undelivered one. A link share's token is the exception (T-601, D-30): the person
needs the URL at once, and a job must never carry a token, so `app.create_share` makes the 32 bytes in the database
(`gen_random_bytes`), stores the SHA-256 and returns the token once to the sharer's browser; it is never logged or
stored, and the web's Sentry scrubber redacts `/share/<token>` like `/invite/<token>`. A revoked, expired or unknown share token gets the identical `unknown` answer, and revoking a share never
touches `public.verify_reference` (BE-27). Share reads are scoped to the report's product (`app.shares.product_id`).
Buckets are private and path-prefixed by workspace id. Supplier uploads land in quarantine, are scanned (ClamAV),
then promoted. Reads of artwork, documents and reports follow the record, not the folder: `private.can_read_object` finds the row
that names the object, requires the object's folder to be that row's workspace, and applies the row's product and
market scope, so a family- or market-scoped member never lists the rest of the workspace's files (#179 DB-5).
`app.register_artwork` refuses a path outside the caller's workspace and product folder (#179 DB-7). Signed URLs are short-lived (minutes for viewing, 7 days for exports).

## Authentication
Email and password or magic link with email confirmation; TOTP MFA. Signing requires `aal2`, checked in the
database (P0292). Removing a member ends the membership, revokes grants and signs out their sessions.
- **Sign-in (T-103).** `/sign-in`; email links (confirmation, sign-in link, reset) return to `/auth/callback` and become
  a session there.
- **Never revealing an account.** A sign-in link is created only for an existing account (`shouldCreateUser: false`).
  The answers to sign-in, sign-in link and reset never say whether an address has an account.
- **Links.** Every expired or used link lands on `/auth/forgot?link=expired`.
- **Two-step.** In the web app, a person with a verified TOTP factor is challenged to `aal2` before reaching a
  workspace or setting a new password through a reset link, and a person holding a signing grant with no factor enrols
  first (`/auth/mfa`). The database enforces `aal2` only for signing (P0292). A token at `aal1` for an account with a
  factor still reads and writes under RLS through the API, outside the web app; whether to require `aal2` in the
  database for such accounts is an open question for a founder (#25, question 7).
- **Staff (T-205, #35 Q6).** `/admin` requires `aal2` for every staff member: one with a verified factor proves it,
  one without enrols first (`/auth/mfa`). The layout, the service-role reader and every staff Server Action check it,
  because a layout is not rendered again on client navigation. The staff RPCs themselves do not check `aal2` yet
  (#25, question 7).
- **Business sign-in (D-27, T-109).**
  - Google and Microsoft OAuth sit beside email and password on `/sign-in` (`components/auth/ProviderButtons.tsx`, for
    onboarding too). Microsoft is the `organizations` tenant, so a personal Microsoft account is refused by Microsoft.
    The flow is PKCE: the provider returns to `/auth/callback?via=oauth`, the code becomes a session at aal1, and the
    T-103 two-step gate applies unchanged. A refusal returns to `/sign-in?problem=…` with fixed text; the provider's
    description is only searched for the hook's marker, never shown or logged.
  - No new account is created for a consumer or free-mail address on any route. `private.before_user_created_hook`
    (Supabase Auth's Before User Created hook) refuses it with 403 and the marker `business_email_required`, against
    `private.consumer_email_domains` (versioned by `list_version`; version `2026-10-29.1` is the domains D-27 names).
    It runs only when a user is created, so existing accounts, sign-ins and identities linked to an existing account
    are never refused. The service role's `admin.createUser` does not call it (test setup and staff only).
  - A sign-up on a new free-mail address is refused, while one on an existing address is answered as usual, so the
    answer can tell whether an account from before D-27 exists on a free-mail address (#138).
  - Google and Microsoft are the customer's own identity providers, not sub-processors.
- **Password reset.** It ends every other session (`signOut({scope: 'others'})`).
- **Audit.** Sign-ins and password changes are audited by database triggers on `auth.sessions` and `auth.users`;
  the password, its hash and every token stay out of the audit, logs and Sentry.
- **Sessions.** The proxy refreshes the session cookie on every request and checks it with Supabase Auth, so a
  revoked session stops at once.

## Secrets and logs
Secrets in Infisical per environment. The service-role key never reaches the browser. Logs and Sentry events carry
ids, never label text, names or emails.

## Personal data (GDPR)
Identity lives in `app.people`, apart from `auth.users`. Erasure tombstones a person ("Former member #n", email and
user id removed) while insert-only records keep the actor id. Full export is free on every plan (BE-44).
Retention periods follow the Workspace Settings design.
