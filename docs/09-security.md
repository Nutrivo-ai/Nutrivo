# 09 · Security and privacy

## Tenancy
Every `app` table has RLS. Membership is derived from `auth.uid()` through `private` helpers; no policy trusts a
workspace id from the request. Scope narrows a membership to families and market nodes (a region id covers its
children). External members and `access_ends_at` are enforced in the same helpers. Staff access comes from
`app_metadata.nutrivo_staff`, which only the Supabase admin API can set. The anon role reaches nothing in `app`
or `ref` and can execute only `verify_reference` and `coverage_snapshot`. On the hosted projects the grants are the
migrations' only: no table writes for anon or authenticated, no automatic exposure of new tables, and Queues never
exposed through PostgREST (D-26).

## The record
Insert-only tables (docs/03-data-model.md) have privileges revoked and a rejecting trigger, so even the service key
and the table owner cannot rewrite history. Certificates form a hash chain per workspace. Every event stamps the
actor's external flag and the ruleset version at write time.

## Tokens and files
Invitation, document-request and share tokens are 32 random bytes generated by the worker; only their SHA-256 is
stored; they expire and are single-use where it makes sense. Job payloads never contain tokens or secrets. An
invitation token is minted inside the `notify` job and exists only in that process and in the email; a retry mints
a new one, which replaces the undelivered one.
Buckets are private and path-prefixed by workspace id. Supplier uploads land in quarantine, are scanned (ClamAV),
then promoted. Signed URLs are short-lived (minutes for viewing, 7 days for exports).

## Authentication
Email and password or magic link with email confirmation; TOTP MFA. Signing requires `aal2`, checked in the
database (P0292). Removing a member ends the membership, revokes grants and signs out their sessions.
- **Sign-in (T-103).** `/sign-in`; email links (confirmation, sign-in link, reset) return to `/auth/callback` and become
  a session there.
- **Never revealing an account.** A sign-in link is created only for an existing account (`shouldCreateUser: false`).
  The answers to sign-in, sign-in link and reset never say whether an address has an account.
- **Links.** Every expired or used link lands on `/auth/forgot?link=expired`.
- **Two-step.** In the web app, a person with a verified TOTP factor is challenged to `aal2` before reaching a
  workspace or setting a new password through a reset link, and a person holding a signing grant with no factor enrols
  first (`/auth/mfa`). The database enforces `aal2` only for signing (P0292). A token at `aal1` for an account with a
  factor still reads and writes under RLS through the API, outside the web app; whether to require `aal2` in the
  database for such accounts is an open question for a founder (#25, question 7).
- **Password reset.** It ends every other session (`signOut({scope: 'others'})`).
- **Audit.** Sign-ins and password changes are audited by database triggers on `auth.sessions` and `auth.users`;
  the password, its hash and every token stay out of the audit, logs and Sentry.
- **Sessions.** The proxy refreshes the session cookie on every request and checks it with Supabase Auth, so a
  revoked session stops at once.

## Secrets and logs
Secrets in Infisical per environment. The service-role key never reaches the browser. Logs and Sentry events carry
ids, never label text, names or emails.

## Personal data (GDPR)
Identity lives in `app.people`, apart from `auth.users`. Erasure tombstones a person ("Former member #n", email and
user id removed) while insert-only records keep the actor id. Full export is free on every plan (BE-44).
Retention periods follow the Workspace Settings design.
